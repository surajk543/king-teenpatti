The Go server removes the 3,000-player ceiling

Same machine, same database, same 4,000-player ramp. Node saturates one core at 3,000 players and its acknowledgement latency climbs to a quarter of a second at 4,000. The Go port answers in 5 ms at 4,000 while spreading its work across cores, and its throughput is still rising with the player count.

Node's CPU column is the share of one core; the process is single-threaded, so 109% is the ceiling. Go's 180% is 1.8 of 12 cores with room to grow. "lag p99" is Node's event-loop delay and Go's scheduler latency, the closest equivalents.

Why Node flattens and Go does not

Every move is one Postgres transaction plus JSON work on the game state. In Node all of that runs on a single thread. At 3,000 players that thread is fully busy (102%), so from there on more players only add queueing: the ack latency at 4,000 is dominated by moves waiting their turn on the event loop, and 160 database requests pile up behind it because the callbacks that would release pool connections are themselves waiting.

The Go server runs one goroutine per table, so 750 tables spread over 12 cores. Each table is still strictly serial, exactly the order guarantee the Node queue gave, but tables no longer wait for each other. The pool queue stays near zero and the ack time stays at the cost of the transaction itself. The next limit is Postgres sharing the host's cores, which is where the earlier multi-worker analysis also pointed.

What was verified before this measurement

  • 554 Go tests across 11 packages, all green under the race detector, mirroring every Node suite plus property and concurrency tests.
  • 141 black-box parity tests run against both servers over the wire: REST, raw Engine.IO framing, lobby, full hands, sideshow, invalid moves, resume, money, metrics. Both pass.
  • Identical event streams for a scripted three-player scenario on Node and Go, normalised and diffed per socket, plus identical ledger rows.
  • Differential engine tests: 22,100 hand evaluations and 194,569 chat-sanitising inputs identical between the JavaScript and Go engines; two scripted hands produce 346 identical records through both rule engines.
  • Real clients: the production bots and the unchanged Flutter APK played against the Go binary. A tap on Chaal produced a ledger row with the app's own action id; a force-stop mid-hand resumed with "Welcome back".
  • Sessions carry over: tokens minted by Node verify in Go and vice versa, so phones stay signed in through the switch.
  • Two 5-minute soaks with churning bots on all three table types: 164 hands, pots up to 2.3 lakh, zero data races, goroutines back to baseline, every wallet equal to its ledger sum.
  • Four adversarial reviews (money, leaks and hostile input, concurrency, Flutter wire compatibility) found and fixed 10 issues, 4 of them present in the Node server too; 0 card or chip leaks.

Fixed along the way

These were found by the reviewers with failing tests first. The first four exist in the Node server as well.

  • A settlement refused by the database was lost for good when the table was destroyed before the retry landed. Go now finishes the idempotent write off the table.
  • A settle and a boot on shared wallets could deadlock through a foreign-key lock taken out of order. Wallet locks now come first.
  • A player could block another player's 25,000-chip milestone forever by reusing its ledger key as a bet's action id. Reserved key shapes are refused.
  • A join finishing on a socket that had just been replaced left the seat without a live viewer or a grace timer.
  • Two simultaneous sign-ins for one account both stayed live; a stale kick could remove a player from the table they had just moved to; a public room:create skipped stake and chip checks.
  • Go-only: a nested-array payload cost 2.8 s of CPU per message; per-connection header retention was 64× Node's; a hung database statement could freeze a table's actor. All three now bounded.

Deploying

The Go binary listens on the same port, reads the same .env, exposes the same game_* metrics and serves the browser client, so nginx, Prometheus and the Grafana game rows do not change. Process metrics move from nodejs_* to go_*; the dashboard's runtime row and three alerts are updated in the branch.

  1. Push the go-server branch and pull it on the host.
  2. bash go-server/ops/build.sh as deploy: installs Go if missing, builds go-server/bin/gameplay.
  3. sudo bash go-server/ops/install-go-server.sh: backs up the Node unit, installs the Go binary as gameplay.service, restarts, verifies /health.
  4. Run the 4,000-player ramp against production and compare with run 7 (p95 409 ms at 4,000, one core saturated).
  5. Rollback at any time: sudo bash go-server/ops/rollback-to-node.sh.
Method. Both servers ran on the same 12-core development machine against the same local PostgreSQL 18, each in its own schema, with PG_POOL_MAX=50 and the production table menu. The load generator (tools/ramptest.mjs, one Node process) ran on the same machine and added blind-200 players in stages of 500, 1,000, 2,000, 3,000 and 4,000, holding each for 45 s. Numbers are per stage from the generator's JSON reports. Because the generator shares the machine, absolute figures are conservative for both servers; the comparison between them is like for like. Production reference: run 7 on 8 Sep 2026 measured Node at p95 409 ms with 4,000 players on the 4-core host.
