The bottleneck is not the game server

What the gap means

The four cores are 88% busy while the game process accounts for 44% of them and Redis for another 4%. Roughly 40% of the machine is being consumed by something other than the game — and on this host the only other things handling per-player work are nginx, terminating TLS and proxying every websocket frame in both directions, and the monitoring exporters.

That is consistent with the shape of the traffic: at 1,835 actions/s each action broadcasts a redacted room:state to every seat at the table, so nginx is relaying on the order of 9,000 messages a second through 14,000 TLS sessions. This remains a hypothesis, not a measurement. A per-process CPU sample under sustained load is the test that would settle it, and it has not been captured: every attempt was defeated first by the load generator’s own connection bursts and then by the upstream filter described in the correction below. Until that sample exists, the honest statement is narrower — the game server, Redis, the database and memory all have headroom at the throughput ceiling, and something else on the host does not.

Cores, memory and the shape of growth

Correction: a finding I withdrew

An earlier version of this page reported that the server drops roughly one in ten new connections when 120 arrive at once, and recommended fixing “connection admission” before a restart discovered it. That was wrong, and it is withdrawn.

What it actually was

The drops were real, but they were happening on the network path between the load generator and the host — not at the server. The controlled test:

Where the burst came fromPathResult
Load generator, over the internetWAN → nginx → TLS 14 of 20 — six SYNs unanswered
The production host itselfloopback → nginx → TLS 20 of 20, ~100 ms each
The production host itselfloopback → nginx → TLS 40 of 40
The production host itselfdirect to Go, no nginx, no TLS 40 of 40
 Identical burst, two origins. The server accepts every one; only the internet path drops them.

Corroborating evidence: the kernel recorded zero ListenOverflows, ListenDrops and syncookies since boot; conntrack sat at 1,456 of 262,144; there is no firewall rule, and fail2ban is inactive. Nothing on the host dropped anything. The failures are consistent with the provider’s upstream DDoS protection treating a burst of SYNs from one source address as an attack — and by the end of testing that filter was dropping even single requests from the generator, while the same request from the host succeeded in 20 ms.

Why it does not affect real players: the filter keys on source address. Thousands of players reconnecting after a restart arrive from thousands of distinct addresses, which is exactly the pattern it ignores. A reconnect storm was never the risk this measurement implied.

The ladder results above are unaffected — they were measured on connections already established, and the ladder paces its arrivals in batches, which is why it never tripped the filter. What the withdrawal costs is the corroboration for the CPU attribution in the previous section: that argument now rests on the CPU measurements alone.

What the numbers say to do next

  • Capture a per-process CPU sample at 6,000+ players — this is the only thing that matters next. The 40% gap is the whole story of the 1,835/s ceiling and it is still unattributed. Run it from a host the provider’s DDoS filter does not throttle (a second cloud instance, or the game host itself), sampling ps/pidstat during a sustained hold. Everything below is guesswork until this exists.
  • Set the serving target at 4,000–5,000 players per host for now. That is the last stage before the knee, at p95 33 ms with every component under half utilised.
  • Test a reconnect storm explicitly. Sustained 14,000 and a cold arrival of 8,000 are different limits, and only the first has been measured.
  • Raise shared_buffers from the stock 128 MB. Not implicated in this run — the pool stayed idle — but it remains undersized for the box and would matter again if write volume grows.
  • Nothing to do about the database write path. It was the bottleneck two builds ago at 660 write IOPS and 16% iowait; it is now invisible in the profile.

Method, and what to distrust

Eight stages, 60-second hold each, driven by tools/ramptest.mjs across eight generator processes on a 12-core machine. Bots are guest accounts that join blind 200 tables and play real hands — see, chaal, raise, pack, show, chat. Latency is the client-observed acknowledgement round trip over TLS. The run stops on p95 above 3,000 ms, errors above 10%, fewer than 90% connected, or /health going away.

Three honest caveats:

  • Two harness bugs had to be fixed to get this run. In multi-worker mode the parent counted connections before its settle sleep rather than after, reporting 840/1000 when the server held all 1,000 sockets with zero failures — which looked exactly like a server refusing connections. Separately, 29% of the bot accounts had drifted outside the playable chip band across months of previous tests, so they could not be seated at all.
  • 51 accounts still could not seat every stage (47 over the entry cap, 4 short of the boot). That is the server correctly enforcing requirement 30, not a fault, but it means each stage ran with ~51 fewer active players than its label.
  • The CPU is attributed by elimination, not by per-process measurement. The host saturation (87.6%), the game server’s share (44%) and Redis’s (15% of one core) are each measured directly; what consumes the rest is not. Five attempts to capture a per-process sample failed — the first few because the generator could not establish connections fast enough, the rest because the upstream filter had by then throttled the generator’s address entirely. This is the one open question in the report.
  • One finding was published and then withdrawn — see the correction section. It claimed a server-side connection-admission limit; it was the test rig. The ladder measurements are unaffected.

The server was never restarted during or after the ladder — it held 15,836 sockets, shed them, and returned to idle on the same process. One error in roughly 1.1 million actions.
