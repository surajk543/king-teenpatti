Bottleneck and feedback

The bottleneck

The load generator's own internet link — not the server. From 5,000 players on, the game's throughput stopped growing at about 1,750 moves a second (411 → 808 → 1,203 → 1,574 through 4,000 players, then 1,761, 1,748, 1,751, 1,745, 1,745, 1,750) while every latency the generator measures — moves, logins, connects and its own /health calls — climbed together. At that same point the production host's outbound traffic, which had grown by about 8.5 MB/s per 1,000 players, went flat at 46–48 MB/s (≈ 370–385 Mbit/s). Measured the same evening, this generator machine downloads at 288–437 Mbit/s, while the production host uploads at 1,164 Mbit/s and downloads at about 2.6 Gbit/s. Every player's traffic had to come down one home connection, and that connection filled.

Inside the server nothing was near a limit, even at 10,000 players: host CPU 27% (no core above 32%), the game process 1.6 of 8 cores, the Go scheduler's latency p99 0.4 ms, RAM 7.3 of 16 GB, PostgreSQL 51 of 100 connections with at most 5 active, the disk 22% busy at 6–8 MB/s of writes, nginx about 30% of one core. The latency above 5,000 players is queueing on the generator's downlink, so the server's own ceiling lies above 10,000 players, and one home connection could not reach it.

What production handled

  • 10,000 players at once — 9,892 connected (98.9%), 9,838 live sockets, 1,768 tables, 4,733 hands a minute, 18 failed moves out of about 78,700 in the hold (0.02%).
  • Up to 4,000 players the game was as fast as it gets: move acknowledgement p95 26 ms and p99 27–29 ms at every stage, with throughput growing exactly in step with the players.
  • From 5,000 players p95 rose from 369 ms to 1,522 ms and p99 from 829 ms to 3,668 ms (10,000), with the worst single acknowledgements at 14–44 s — what a saturated last mile looks like, not a slow server.

Where the server itself will run out (projected from 1,000–4,000 players, where the generator kept up)

  • First: network egress. The server sends every player about 8.5 KB/s — a full, per-viewer room:state after every move at the table. At the 1,164 Mbit/s this host measured, that is roughly 17,000 active players before its own uplink is full.
  • Then: CPU. The host's CPU rose about 6.2 points per 1,000 active players (the game process about 0.3 cores): 100% near 16,000, so plan on about 11,000 to keep 30% in hand.
  • Memory is far off: about 0.53 GB of host memory per 1,000 players (the game about 120 KB a player), room for ~25,000 on 16 GB.
  • PostgreSQL and the disk are far off: ~330 transactions/s at 4,700 hands a minute with 1–5 of the game's 50 pooled connections busy, and the disk at a fifth of its time.

Feedback

  • To find the real ceiling, generate the load from the cloud, not from one office line. Two or three VMs in the host's region with 1 Gbit/s each, the same ramptest.mjs split with --idOffset, would carry 20,000+ players and show which of the projected limits arrives first.
  • Compress the websocket (permessage-deflate) or send changes instead of the whole table after every move. room:state is JSON repeated per viewer; it typically compresses 5–10×. That is the single biggest lever: it moves the egress limit from ~17,000 players to well past the CPU's, and it cuts every player's mobile data by the same factor.
  • Put the monitoring bundle on this host. Production runs no Prometheus or exporters, so these numbers exist only for the minutes of this test; go-server/ops/monitoring would keep them all the time.
  • Restore the login limits. REST_LOGIN_RATE_LIMIT=60 and REST_WALLET_RATE_LIMIT=120 were set to 0 for this test; put them back in the .env and restart the service.
  • The test left 10,000 guest accounts (LoadBot0–LoadBot9999) in the production database, each with its 3,00,000 welcome chips (300 Crore in all). A re-run reuses them. users rows cannot be deleted by design; if they should go, the account-deletion path empties their wallets through the ledger.
  • Everything else can stay as it is for this size: a pool of 50 against max_connections 100, nginx's 16,384 connections per worker and the service's 65,536 open files all held 10,000 players with room to spare.

Methodology and how to read this

Where each figure comes from

  • The generator (tools/ramptest.mjs, 8 worker processes): players, connected, joined, login and connect times, the action-acknowledgement percentiles, actions/s, hands/min, errors, disconnects, join refusals, health RTT and its own lag. Every latency is a client-side round trip from the generator machine: it includes the network path, TLS and nginx, not just the server's work.
  • /health, polled by the generator every 5 s of each hold: the game process's RSS, heap, CPU share of one core, scheduler latency, goroutines, sockets, players, tables and pool waits. These are what the ramp JSON's host block holds and what this report falls back to when no host JSON is given.
  • Prometheus on the host (tools/host-metrics.mjs): node_exporter for per-core CPU, I/O wait, memory and the interface counters; the game server's own /metrics for its CPU seconds, RSS, goroutines, threads, sockets, tables, move-processing and ledger-transaction histograms and live-store timings; postgres_exporter for backends, max_connections, active queries, commits and rollbacks; redis_exporter for memory, clients, commands and per-command time; the nginx exporter for connections. Each is aggregated over the stage's exact hold window (mean and max of 15 s samples), so a row describes the same seconds the generator measured.
  • The host sampler (tools/loadtest/host-sampler.py), what no exporter records: per-process CPU for postgres, gameplay and redis-server from /proc, host CPU, interface bytes, Redis INFO, and Redis latency as a client on the host sees it (twenty PINGs on a fresh loopback socket). Its lines are folded into each stage's row and, when the whole file is given, drawn across the run.

The stop rules

A stage ends the run when its action p95 is above 3,000 ms, its refused-action rate above 10.0%, fewer than 90% of its players are connected, or /health stops answering; the ramp also gives up while adding players when more than 5% of the newest fail to connect. The last stage before that is the ceiling; a run with no ceiling was held to its last listed stage.

Validity

The generator's own lag chart is the check on everything else: it is how late a 100 ms timer fired in the generator process, and if it climbs with the player count the laptop is the bottleneck and the latencies above it are suspect. Below a few milliseconds the figures are the server's.

Caveats

  • Everything ran at one table kind, blind, boot 200; other stakes and the poker rooms write the same checkpoints but deal and settle at their own pace.
  • The resident bot fleet and any real players share the server: socket, player and table counts include them, and the "before" line in the header says how many were there.
  • The generator's guests are reused between runs (ramp-bot-<n>), so login is an upsert of an existing account, not a first sign-in with a welcome bonus.
  • Exporters scrape every 15 s and the sampler every few seconds, so a peak shorter than that is averaged away; the maxima are the largest sample, not the largest instant.
