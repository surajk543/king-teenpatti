Stages not reached

Reading the profile

Up to 4,000 players the server answers a move in 62 ms or less at the 95th percentile, of which 26 ms is the network. Throughput grows in step with players (400 → 1,358 actions/s) and the four cores are three-quarters busy.

5,000 to 7,000 is the knee. Throughput keeps rising to its peak of 1,625 actions/s at 7,000, but the host reaches 95% CPU and the p95 climbs from 62 ms to 555 ms as moves queue for the database. The Go process itself never uses more than 1.8 cores; PostgreSQL takes the rest.

From 8,000 the host is saturated (all cores 97–99%, I/O wait 22–30%). Throughput falls back to 1,100–1,400 actions/s because work is now spent on contention rather than moves, and the tail runs into seconds. At 15,000 the p95 crossed the 3 s stop rule and the run ended on its own. No stage produced a single refused move or a server error.

What would move the ceiling: a database on its own host (it consumes about two of the four cores plus all of the disk), more cores on the game host, or both. The game server code has headroom: on a 12-core machine it held 4,000 players at 5 ms.
