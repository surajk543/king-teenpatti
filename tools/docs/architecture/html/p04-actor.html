FlowsA table is an actor

Every table owns one goroutine. Anything that reads or changes the table is a closure posted to that goroutine, and the caller waits until it has run. Two moves, a move and a turn timer, a leave and a database answer: none of them can interleave, because they queue. There is no lock inside a table.

The same shell carries Teen Patti tables and poker rooms: Actor (the mailbox), LiveState (the Redis snapshot and its fence) and Settler (the hand-end retry chain) live in actor.go, and both game.Table and poker.Table embed them.

The rules that keep it deadlock-free

  • Exported methods post, unexported ones never do. Table.Act calls t.run(…); t.act, t.bet, t.endHand run on the actor and must not call run again, or the goroutine waits on itself.
  • A listener never calls back into its table. Events (game.Listener) are delivered on the actor goroutine. The kick path, which must remove a player, runs in a goroutine of its own.
  • Timers post. The turn clock, the sideshow clock and the start delay fire through clock.AfterFunc and post a closure. Each carries a token, so a timer that fires after the turn already moved finds a different token and does nothing.
  • Panics stay local. A panic inside one move becomes an internal_error for that move; the table keeps running.
  • Readers that cannot wait use atomics. PlayerCount, IsFull, State and Version are lock-free, so the RoomManager can scan tables while holding its own mutex.
  • The RoomManager's mutex guards only its maps and is never held while a table is called. Each player also has a seat-lock stripe: every door into a seat and every lobby-only wallet change takes it, so a purchase can never land between a join's wallet read and its seat.
After every closureIf the closure changed anything a player can see, the whole table is serialised once and saved to the live store under the next sequence number. A save refused as stale means another process owns the table: it is fenced, accepts nothing more, and is torn down without settling a hand it no longer owns.

FlowsOne move, from the tap to every screen

A bet is the hot path, and it never touches PostgreSQL. The socket layer checks rate limits, the table validates and applies the move in one closure, every viewer gets their own redacted snapshot, and the snapshot is saved to Redis as the closure ends.

  • Refusals carry a code. Every refusal is a GameError{Code, Message} with a snake_case code (not_your_turn, invalid_bet, insufficient_chips …). Clients compare codes, never messages. A refusal arrives twice on purpose, as the ack and as game:error; clients dedupe.
  • Every move is idempotent. The client sends a fresh actionId with each move. The table remembers the ids a player used this hand and refuses a repeat with duplicate_action, so a retried request is never charged twice.
  • Amounts are never trusted. A bet must be exactly a rung of the ladder the table computes (betOptions); anything else is invalid_bet.
  • Seeing your cards is not a move. see is free, allowed off-turn, and does not reset the turn clock.
