FlowsDropped connections

Phones lose their network, get locked, and switch apps. A seat survives all of that for a while, and after that the way back to the table survives a while longer.

{{svg:resume}}
  • The handshake carries the JWT (handshake.auth.token) and the app's platform and version. It is refused with a code (invalid_session, account_disabled, session_replaced, update_required, maintenance) and such a refusal is final; a network failure is retried by the client.
  • One live socket per account, one signed-in device. Every login counts a new session (user_sessions.version, signed into the token as sv). A newer login ends the older device's socket with session:replaced, and the new device's connection takes over the seat.
  • The grace. When a socket drops, the seat is marked disconnected and held for 60 seconds. The turn clocks keep running. Reconnect inside the grace and the server sends room:joined with the live hand.
  • The resume offer. When the grace runs out the player leaves the table, and the table is offered back for 10 minutes: the next session:ready carries resume, and the app rejoins with room:joinCode. An idle kick of a player with no live socket leaves the same offer.
  • The app helps. Sent to the background while seated, the Flutter app closes its socket after 8 seconds, which starts the server's grace at once instead of letting three turn clocks run out unanswered.
  • Silent drops are noticed by the Engine.IO heartbeat (ping every 20 s, 25 s timeout).

FlowsBoot, restore and shutdown

Configuration is read once. A value that does not parse stops the binary with the key named, and production refuses to start on a weak JWT secret or without the R2 keys. Everything that is built afterwards holds the same immutable Config for the life of the process.

{{svg:boot}}
  • Migrations run at every boot. There is no schema history table: the server applies every embedded script every time, so each one is idempotent. gameplay -migrate runs the same step alone, which is what a deploy does before it restarts anything.
  • The table catalogue (engines, categories and every lobby table with its figures) is read once, from PostgreSQL when TABLE_CONFIG_SOURCE=db, otherwise composed from the environment. An edit to the rows applies at the next restart, to tables opened after it.
  • Restore. Every table snapshot in Redis is rebuilt as a running actor. The first bytes of a snapshot say which game it is, and the matching factory restores it. Seats come back disconnected and are held for the grace; timers resume with what was left of their deadlines. A turn whose deadline passed while the process was down gets a fresh clock rather than an instant timeout.
  • Without Redis (REDIS_URL empty) the live store is in-process memory: a single instance whose tables do not survive a restart. Players rejoin; nothing is reconstructed.
  • Shutdown. On SIGTERM the socket server closes first. With Redis, every table is suspended: its clocks stop, a final snapshot is saved, and the next process resumes the hand where it stopped. With the in-process store, every live pot is settled instead (to the first active seat, reason all_left), because nothing would come back. Then the statistics still waiting are flushed and the process exits, all within max(8 s, statement timeout + 5 s).
Two owners, neverEvery snapshot is saved under a sequence number with a compare-and-set. A process that finds a newer sequence than its own knows another process owns that table, and stops touching it.
